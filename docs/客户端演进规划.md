# 客户端演进规划

> 本文记录桌面更新器从「单机日志采集工具」向「集中化可观测 + 插件自愈」演进的架构结论、
> 分阶段任务与待决事项。是活文档，随进展更新。
>
> 讨论日期：2026-08-20。CLAUDE.md 只保留一行指向本文，架构内容不复制过去（防漂移）。

## 1. 背景

领导提出四条需求，并给出一张「多客户端 + 中心C + AI」的架构图：

1. 客户端跟插件建立心跳，无心跳自动重启浏览器插件
2. 插件记录日志通过客户端转发到本地日志文件
3. 客户端开放局域网端口，能让 AI 请求接口获取本地日志文件
4. 请求接口获取插件异常情况让 AI 分析

图中要素：客户端 A / B / 本机（各采购虚拟机上的更新器实例）、客户端(中心C)（汇聚节点）、
虚线（各端向中心汇聚）、左侧节点（AI 拉取分析）。

**意图解读**：从「日志只躺在每台机器本地」升级为「日志可被远程集中读取并喂给 AI 分析」，
同时插件异常能自动恢复，不再依赖人工发现。

## 2. 架构结论

### 2.1 三层职责

```
插件（浏览器内）        产生日志、干采购的活
    ↕ 本地 HTTP
客户端（中介）          落盘 / 心跳判定 / 自愈执行 / 代理上报
    ↕ HTTPS
Web 中心（服务器）      汇总 / 展示 / 给 AI 提供数据
```

**客户端的定位是「中介」**——它存在的理由就是做插件做不到的事：

| 插件的限制 | 客户端补上 |
|---|---|
| 浏览器沙箱内写不了文件 | 落盘日志（客户端最初诞生的理由） |
| 浏览器关了它就没了 | 常驻进程，离线缓存、断网补传 |
| 里面放凭证等于公开 | 保管上报 token |
| 自己死了自己发现不了 | 外部观察者，心跳判定 |
| 碰不到操作系统 | 重启 Chrome、模拟快捷键开侧边栏 |

最后两条尤其关键：**领导第 1 条需求只有中介能做**，插件（自己卡死救不了自己）和
Web 中心（在远端够不着采购机器的操作系统）都做不到。

### 2.1.1 为什么有了 Web 中心，日志仍要经过客户端

常见疑问：既然要传到中心，插件能不能跳过客户端直连？**不能**，四个理由：

1. **断网即丢**：插件活在浏览器里，浏览器一关，内存里没发出去的日志跟着蒸发，没有"下次再传"
   的机会。离线缓存补传只有常驻进程做得到。
2. **本地日志会消失**：现在断网也能在「日志查看」页翻本机日志；直连后本地不留，网一断排查
   现场直接没了，且现有按天分文件/异常归集/7 天保留全部作废。
3. **凭证会暴露**：上报 token 放插件里 = 放浏览器里，打开 DevTools 就能看到，网页脚本也能
   读走，拿到即可灌假日志。
4. **重复解决跨域**：插件从 1688 页面直连公网中心又是一次跨域，且是对公网开放，风险远大于
   本机 127.0.0.1。

### 2.1.2 客户端会不会太重——职责边界判断标准

客户端承担的每一条都是「只有它能做」的事，没有一条是「本可放别处却塞给它」：
落盘（插件写不了文件）、心跳判定（需外部观察者）、自愈执行（只有桌面进程碰得到 OS）、
代理上报（需常驻才能补传、才能安全存凭证）、更新插件（原有职责）。

真正会让它变重的设计已被主动避开：

| 若这样设计 | 会变重 | 本方案的选择 |
|---|---|---|
| 开对外服务等中心来拉 | 要做鉴权/脱敏/白名单三件套 | 推模式，零入站端口 |
| 存历史日志 + 做检索 | 要数据库与索引 | 只留 7 天文本，检索归中心 |
| 做异常聚合分析 | 要统计逻辑 | 归中心 |
| 做管理界面 | 要一套前端 | 归中心 Web |
| 心跳判定放中心 | 要维护长连与网络异常处理 | 判定在本地，中心只知情 |

定位类比：**监控 agent**（如 zabbix/datadog agent）——本机采集 + 上报 + 本地处置，重活在服务端。

> **后续开发的约束**：新功能要放进客户端前，先问「这件事是不是非得在本机、非得常驻、
> 非得碰操作系统？」三个都不是，就该放 Web 中心。防止功能蔓延把客户端堆重。

### 2.2 中心做成 Web 服务，不是「中心客户端」

图上写「客户端(中心C)」，但按其职责应做成**服务器上的 Web 服务**：

| | Web 中心 | 中心客户端 |
|---|---|---|
| 可用性 | 服务器 7×24 | 办公机会关机/退出 |
| 谁能看 | 浏览器打开即可，多人可看 | 得登那台机器 |
| 存储 | 数据库，可检索 | 文本文件撑不住十几台 |
| AI 对接 | 现成 HTTP 接口 | 得另做 |
| 现有基础 | 已有 chainai.cjdropshipping.cn + nginx | 要新做 Tauri 应用 |

采购虚拟机「通常只有 C 盘」（见 CLAUDE.md 项目背景），把十几台的日志汇总到一台办公机上
不现实。

### 2.3 通信用推模式（客户端主动推中心）

| 维度 | 拉模式（中心来取） | 推模式（客户端去送） |
|---|---|---|
| 采购机器开端口 | 每台都要开入站端口 | **零** |
| 安全措施份数 | ×N 台，任一台配错即缺口 | ×1，只在中心 |
| 机器离线 | 那段数据永久拿不到 | 本地缓存，上线补传 |
| IP 变化 | 要维护（虚拟机 DHCP 会变） | 无影响 |
| 新增机器 | 配防火墙 + 登记 IP | 填地址即可 |
| 实时性 | 即时 | 有推送间隔（可接受） |
| 与现有架构 | 反向，要新开对外服务 | 同向延伸（插件→客户端本就是推） |

拉模式唯一优势是实时性，而日志分析恰好不需要实时。**推模式在其余维度全面占优。**

### 2.4 自愈判定放在客户端本地，不绕中心

```
✅ 插件 → 客户端判定超时 → 客户端立即处置 → 顺便上报中心知情
❌ 插件 → 客户端 → 中心判定 → 中心下发指令 → 客户端执行
```

理由：中心挂了/网断了本机自愈照常工作；判定在本地是秒级反应；中心职责更单纯。

**附加好处**：阶段一（心跳自愈）因此**完全不依赖 Web 中心**，三个项目不必同时开工。

中心该做的是本机看不到的事：跨时间规律（某台今天重启 5 次）、跨机器关联（十几台里 3 台同时出问题）。

## 3. 客户端 ↔ 插件通信设计

### 3.1 形态：插件轮询，响应捎带指令

**硬约束**：客户端**无法主动连插件**（插件活在浏览器沙箱里，没有可被连接的地址），
所以只能插件主动来问。

```
每 5 秒：
插件 ──→ POST http://127.0.0.1:17653/heartbeat
         { pluginName, sidepanelOpen, taskRunning, acked: ["cmd-122"] }

客户端 ←─ 200
         { commands: [ { id: "cmd-123", type: "reload" } ] }

插件执行 → 下次心跳带 acked:["cmd-123"] → 客户端出队
```

**ack 机制不可省**：心跳是轮询，同一条指令会被反复取走，没有 ack 会出现
「reload → 重新心跳 → 又拿到同一条 reload → 又 reload」的无限循环。

### 3.2 两条独立路径

| | 路径 A（走通道） | 路径 B（走系统） |
|---|---|---|
| 前提 | 插件还活着 | 插件死了，取不走指令 |
| 执行者 | 插件自己 | 客户端直接操作 OS |
| 用于 | reload、立即上报、改配置 | 重启 Chrome、模拟快捷键开侧边栏 |

**打开侧边栏走路径 B**，不走通信通道——因为 `sidePanel.open()` 必须由用户手势触发，
插件收到心跳指令时调会被 Chrome 拒绝。

## 4. 打开侧边栏的实现原理

### 4.1 Chrome 的硬规则

`sidePanel.open()` **只能由用户手势触发**（防扩展乱弹面板）：

| 谁来调 | 认不认 |
|---|---|
| 用户点扩展图标 → 插件在回调里调 | ✅ |
| **用户按快捷键 → 插件在回调里调** | ✅ **键盘也是手势** |
| 插件在定时器里调 | ❌ |
| 插件收到网络消息后调 | ❌ |
| 桌面程序直接调 | ❌ 碰不到这个 API |

### 4.2 解法：客户端模拟按快捷键

插件已注册快捷键 **`Ctrl+Shift+L`**（`wxt.config.ts` 的 `commands.toggle_sidepanel`
→ 处理逻辑在 `background.ts:226-230` 调 `sidePanel.open()`）。

```
客户端 → 调用 OS 的模拟按键 → 操作系统发出键盘事件
                                    ↓
                        Chrome 收到 Ctrl+Shift+L
                                    ↓
                    触发插件 commands.onCommand
                                    ↓
                        插件调 sidePanel.open() ✅
```

**核心是「借道」**：桌面程序碰不到浏览器扩展，但碰得到操作系统；操作系统能给 Chrome 发键盘事件。

### 4.3 与旧方案的区别（重要）

2026-07-30 的 commit `af1233b` 移除过「打开侧边栏」功能，结论是
「Chrome 未提供外部进程强制展开扩展侧边栏的接口，效果不稳定」。

| | 旧方案（已移除） | 新方案 |
|---|---|---|
| 手段 | 拼 `chrome-extension://<id>/sidepanel.html` 让 Chrome 导航 | 模拟按快捷键 |
| 本质 | 在标签页里打开一个 HTML 文件 | 触发扩展的 command 事件 |
| 是否用户手势 | 不是，只是导航 | **是** |
| 结果 | 打开的不是真侧边栏 | 调用真正的 `sidePanel.open()` |
| 依赖 | 要用户配置扩展 ID | 快捷键固定，无需配置 |

**旧方案是绕过 API 模拟效果，新方案是走合法路径触发 API。** 已在 Windows 虚拟机手动
按 `Ctrl+Shift+L` 验证可打开侧边栏。

## 5. 分级自愈策略

| 级别 | 触发条件 | 动作 | 用户感知 |
|---|---|---|---|
| 一级 | 心跳超时 ~20s（半死：JS 还能跑） | 下发 `reload` 指令，插件调 `runtime.reload()` | 无感（侧边栏没关，reload 后自动恢复） |
| 二级 | 心跳全断 ~2min（全死：SW 崩溃） | 重启 Chrome → 模拟快捷键开侧边栏 | 浏览器重启 |

**复用插件已有保护**：`isAnyTaskRunning()`（`background.ts:1274`）与 `PENDING_RELOAD`
机制（`background.ts:1261`）——有任务在跑时标记待重载，不打断任务。

**必须配防护**：冷却期（如 30 分钟内最多重启一次）+ 累计次数上限 + 超限后停手只报警。
否则某台机器因网络异常一直收不到心跳，会陷入「无限重启 Chrome」，比插件卡死严重得多。

**能力边界**（需向领导说明）：

| 能做到 | 做不到 |
|---|---|
| 插件半死时静默重载，无感 | 全程零人工介入的前提是快捷键可用 |
| 检测异常并自动恢复 | Chrome 不允许外部程序直接调 API 开侧边栏 |
| 极端情况重启 Chrome 保证进程活着 | —— |

## 6. 环境约束（已确认，简化了设计）

采购虚拟机的实际情况消除了三个原本的顾虑：

| 顾虑 | 实际情况 | 影响 |
|---|---|---|
| 模拟按键会抢焦点 | 虚拟机无人值守，只跑插件 | 无影响 |
| macOS 需辅助功能授权 | 全部是 Windows | 不涉及（macOS 脚本仅本地调试用） |
| 快捷键可能被用户改掉 | 不会被改 | 兜底逻辑可弱化 |

## 8. 分阶段任务

### 阶段一：心跳自愈（可立即开工）

改动范围：`pluginUpdate_rust` + `pms-aichat`，**不涉及 Web 中心**。

客户端侧：
1. 开侧边栏能力 —— 照抄 `build_refresh_all_tabs_*` 三层模式（`lib.rs:233-301`）
2. 重启 Chrome 能力 —— 同上三层模式
3. `/heartbeat` 端点 —— 与 `/log` 并列，复用已修好的 `build_cors_layer()`；状态表记
   `last_seen`/`sidepanel_open`/`task_running`/`pending_commands`（内存态即可）
4. 自愈编排 —— 后台定时检查 + 分级策略 + 冷却期与次数上限

插件侧：
5. 心跳发送 —— 复用 `logForwarder.ts` 模式（失败静默、不阻塞主业务），5 秒间隔
6. 指令处理 —— switch 分发；`reload` 复用已有 `runtime.reload()` + 任务保护
7. ack 回报 —— 执行完的指令 id 下次心跳带回

### 阶段二：集中上报（待领导拍板）

改动范围：`pluginUpdate_rust` + Web 中心（新项目）。

- 客户端侧工作量不大：后台推送任务（批量 POST 已落盘的日志）+ 响应解析取指令 + 断点续传游标
- **真正的工作量在 Web 中心**：后端 API、数据库、前端界面、AI 对接、部署运维

前置：机器身份可靠化（见卡点）必须先做完。

## 9. 卡点清单

### 🔴 需领导决策

- **Web 中心谁做、部署在哪、数据库用什么**
  中心是完整新项目（API + 数据库 + 前端 + 部署），可能比更新器本身还大。
  客户端推送代码必须先知道中心接口形态才能写。
- **是否认可推模式**
  第 3 条原文写的是拉模式（「客户端开放局域网端口」），与架构图上的中心 C 不一致。
  两条路代码完全不同、不可复用，选错整块推翻。

### 🟠 技术卡点

- **机器身份不可靠**
  现在区分机器只靠 `plugin_name`（插件自报的下载目录名，见 `pluginIdentity.ts`），
  取不到时静默回落 `'unknown'`，且插件侧可随意改。集中化后几台没配好的会全叫 unknown。
  **需补客户端侧生成并持久化的机器 ID。不管推拉都要做，越晚做历史数据越脏。**
- **安全三件套**
  `log_server.rs` 有三处注释 + 一个单测守着「只绑 127.0.0.1」，原注释写明跨机器取日志
  必须同时补齐**鉴权、脱敏、网段白名单**；CLAUDE.md 安全红线另写死「新增读取日志接口时
  必须同步收紧 CORS 为来源白名单」（上次放开任意来源的前提是「只写不读」）。
  日志含登录 token / 供应商聊天 / 采购报价，做错是泄露事故。
  选推模式可大幅缓解——安全只在中心做一份，采购机器零端口。

### 🟡 待处理

- **插件日志失败即丢弃、无重试**（`logForwarder.ts` 的 `fetch().catch()` 静默吞掉）
  现在只是「更新器没开时丢日志」，集中化后是「中心也永远看不到」。建议阶段二前补上。
- **虚拟机升级报 500**
  0.2.6 已发布但虚拟机装不上。服务端已验证正常（latest.json 200、exe 200/206、
  4189836 字节、文件头 MZ 合法、连测 5 次无失败），**500 出在虚拟机端**，怀疑代理对
  文件名中的 `%20` 处理不当。待虚拟机侧 curl / nslookup / netsh winhttp show proxy 输出。
  此问题阻塞所有 Windows 端实测。
